## 0. Rules, reading guide and resolved disagreements

### 0.1 Rules that bind every item below (project rules, restated)

1. **Canon by default, AU by choice.** `canon_me3` stays canon. Everything from the Apex reference pack that is not released-game canon lives in the AU presets `prime_apex` ("Apex core") and `apex_legacy` ("Apex legacy, high power") or in AU scenarios/scenes, and carries an AU label on every screen and in every codex entry (§15). **`canon_me3` changes are exactly these, and nothing else:** (a) the canon-anchored calibration of §3; (b) brief-driven additions that are *not* canon and are labelled as such everywhere they appear — Oculus complements on Reaper warships (`SIMULATION_ESTIMATE`: the drone is canon, Reaper warships launching it in a fleet battle is an extrapolation, §13.1), the dreadnought-grade Sol defence platforms (`SIMULATION_ESTIMATE`, §4.2), two `alliance_dreadnought_k` hulls and two SR-2-pattern frigates in the Sol fleets (§4.2, §22.1), the hostile Cerberus strike group at the Final Battle (extrapolation; Cerberus forces were not at the Battle of Earth in ME3, §4.1), the distant engagement layer shown as percentages (extrapolation, §13.3) and the three canon-compatible Reaper tactics (`SIMULATION_ESTIMATE`, §10). Stage D copies this list verbatim into `AU_RULES.md` and `CHANGELOG.md`; no document says "canon untouched".
2. **Provenance.** Every catalogue value carries `CANON_CONFIRMED | CANON_INFERRED | SIMULATION_ESTIMATE | AU_MODIFIED`. The pack's labels map as in §14.1. The pack's "CANON" claims are accepted only after a check against `LORE_REFERENCE.md`; unverified ones stay `CANON_INFERRED` with a verify-note (`PACK_ADOPTION.md` §1 is the audit).
3. **No ripped assets.** Every model, texture, sound and string is original. The pack is ChatGPT-generated reference text supplied by the user, not canon authority. The user's screenshots are study material and are never committed.
4. **Determinism.** `SIM_DT = 0.05 s`, seeded headless simulation; rendering only reads it. Every new mechanic draws randomness only from `sim.rng` (or a child `rng.fork(label)` created once in the constructor) in fixed step order. No `Math.random`, `Date.now()` or `performance.now()` in simulation-affecting code: `tests/lint.test.ts` walks `src/simulation`, `src/data`, `src/timelines`, `src/scenarios`, `src/campaign`, `src/core` and `src/showcase/scenes`; the only allowed exceptions are identifiers and clocks that never reach the simulation — the save-slot id (`src/core/saves.ts`), the campaign id (`src/campaign/engine.ts`) and the injected clock of `src/simulation/profile.ts` (`profile.now`, a constant-zero no-op unless a script or the controller sets it to `performance.now`) — each allow-listed in the lint test by path and pattern. Render-side randomness uses seeded `Rng` instances so Record mode is frame-reproducible.
5. **Honesty.** No unimplemented feature is claimed. Scenes that force events log every forced event and print them. Limitations are listed (§17) and in `KNOWN_ISSUES.md`.
6. **Tests stay green.** The existing 83 unit and 8 e2e tests stay green (with the explicit changes listed in §16); every new mechanic ships with tests.

### 0.2 Decision codes used below

**FINAL** = decided here, implement as written. **TUNE** = the number is the starting value; the implementer measures and may move it inside the stated bounds, then pins the result in a test and reports it. **DEFER** = not in V2, no stub.

## 3. D3 — Canon calibration (FINAL numbers, canon-anchored)

### 3.1 Mechanics (all deterministic, no RNG)

- **M1 — recovery under fire.** `ShipClassDef.barrierRegenUnderFire?: Sourced<number>` (0–1, default 0), copied to `ShipState`. `updateHousekeeping`: `frac = time − lastHitAt > 3 ? 1 : ship.barrierRegenUnderFire; if (frac > 0 && barriers < max && time ≥ regenSuppressedUntil) barriers = min(max, barriers + barrierRegen × frac × dt)`. `reaper_capital` and `harbinger` 1.0; every other class 0. Anchors: "Sovereign's barriers withstood the Citadel fleet" (`CANON_CONFIRMED`) and the concentration-of-fire benchmark (pack claim, unverified — `PACK_ADOPTION.md` §1 #9; worded as §0.3 #2 says).
- **M2 — barrier load threshold.** `ShipClassDef.barrierLoadThreshold?: Sourced<number>` (points, default 0 = off). In `applyDamage(target, raw, weapon, rng, now, opts?: { hitSize?: number })`: `absorbed = min(barriers, amount × eff)`; `load = threshold > 0 ? absorbed × min(1, (opts.hitSize ?? raw) / threshold) : absorbed`; `barriers −= load`; `amount −= absorbed`; `out.barrierDamage = load`. Beams pass the whole burst (`def.damage × beamDuration`) as `hitSize`. Capitals and Harbinger only (threshold 1,000 = 1 DKE). The round is still stopped; the field is only loaded in proportion to the hit.
- **M3 — heat capacity by hull.** `ShipClassDef.heatCapacity?: Sourced<number>`; `applyRulesToShip` returns `(cls.heatCapacity?.value ?? 100) × t.heatCapacity`. Values: dreadnought 200, super_dreadnought 260, carrier 180, cruiser 140 (heavy cruiser 160), frigate 110, fixed_platform 240 (heavy 260), fighters and Reaper classes 100.

### 3.5 The re-measure protocol

### 13.3 Distant engagement layer

There is no hull cap (§21): the live simulation fields what the machine's measured budget allows and the layer represents the remainder. Simulation side (`src/simulation/distant.ts`): `DistantGroup { id, side, faction, label, count, bearingDeg, distanceKm (60–160 compressed), spreadKm, classMix }`, `DistantLayerConfig { enabled, groups, captions: 'apex' | 'canon' | 'none', firstLossAfter? }`, state `{ groups: { id, remaining, losses, firingRate }[] }` advanced at the end of `step()` after `checkEnd` from `sim.distantRng = sim.rng.fork('distant')` (created once in the constructor, so the real battle is bit-identical with the layer on or off — asserted). Loss rate per group per second `λ = 0.0009 × pressure(side) + 0.6 × realLoss(side, 20 s) / 20`, stochastic rounding, no losses before the first real `ship_destroyed` or `firstLossAfter` (30 s). Events `distant_update` every 5 s and `distant_group_broken` below 10 %. `BattleResult` unchanged; the results screen prints a separate "DISTANT ENGAGEMENT (STATISTICAL)" line, which ends in `· AU SCENARIO VALUE` whenever the layer carries Apex counts (`distantSummary(sim)[i].captioned === true`) and prints percentages only otherwise. Groups come from `APEX_SCALE.coalition.byCommand` minus simulated hulls under Apex scenarios (`isApexScenario`, §13.2), and from `count = 12 × simulated` per real fleet under every other rule set (captions without absolute numbers); the layer is switchable under every preset (§4.1) and the canon briefing line names it an extrapolation. Render side (`src/rendering/distant.ts`): drive-light `Points` (≤ 4,096, faction engine colours, slow drift toward the enemy) and tracer-spark `Points` (≤ 8,192, shader-advanced) 600–1,600 units beyond the fleets; 2 draw calls.

## 21. Scale without caps — performance governor, flights and the benchmark ladder (brief §8.2 as amended; FINAL)

### 21.1 The rule

**No fixed per-side cap exists anywhere in V2.** `SHIP_CAP_PER_SIDE`, `HARD_SHIP_CAP`, `ENTITY_BUDGET`, the custom editor's E2 error and per-role `classMax`, and the campaign's `MAX_SHIPS_PER_SIDE = 70` are not built or are deleted. The only hard limits are identity limits (unique hulls, §22.1) and an input sanity bound of 2,000 per class row in the editor (typing protection, not a cap). The simulation and the renderer must scale as far as the machine allows: spatial hashing for targeting, point defence and collision (no O(n²) per step), staggered decision intervals, fighters and Oculi simulated as flights when numerous, instanced rendering for identical hulls, LOD plus the far point cloud, and the statistical distant-engagement layer for whatever exceeds the live budget. A **performance governor** measures step and frame cost at runtime, degrades visuals first and then warns; the player may override every warning.

### 21.2 `PerfBudget` and `PerfGovernor` (pure, `src/core/perfGovernor.ts`; measured by the controller; applied by the renderer)

```ts
export interface PerfBudget { liveHullsPerSide: number; smallCraftPerSide: number; source: 'default' | 'measured'; measuredAt?: string; machine?: string }
export const DEFAULT_PERF_BUDGET: PerfBudget = { liveHullsPerSide: 400, smallCraftPerSide: 160, source: 'default' };
export type GovernorLevel = 0 | 1 | 2 | 3 | 4;
export interface GovernorSample { stepMs: number /* mean sim step cost over the window */; frameMs: number /* mean whole-frame cost */; stepsPerFrame: number /* mean steps actually performed per frame */; hulls: number; smallCraft: number }
export const renderShareMs = (s: GovernorSample): number => Math.max(0, s.frameMs - s.stepsPerFrame * s.stepMs);   // what the visual ladder can influence
export interface GovernorState { level: GovernorLevel; since: number; samples: number; lastSample?: GovernorSample; level4Since?: number }
export const GOVERNOR_TARGET = { frameMs: 16.7, raiseAfter: 1.5 /* s above target */, lowerAfter: 6.0 /* s below 70 % of target */, refineAfter: 20 /* s at level 4 */, budgetFloor: 100 };
// no `stepsPerFrame` here: the brief's 20 steps per frame is the headless gate HEADLESS_GATE (§21.5) and has no meaning in a 1× loop that needs 0.33 steps per frame
export function governorStep(state: GovernorState, sample: GovernorSample, now: number): GovernorState   // pure ladder with hysteresis on renderShareMs(sample), never on stepMs
export function budgetFromLadder(rows: { hulls: number; stepsPerSecond: number; frameMs: number }[]): PerfBudget   // the largest row whose frameMs meets GOVERNOR_TARGET.frameMs
export function refineBudget(budget: PerfBudget, live: number, state: GovernorState, sample: GovernorSample, now: number): PerfBudget   // see "Budget" below
```

- **Measurement** (stage B, `BattleController.loop`): a 1 s rolling window of `stepMs` (wall time of `sim.step()` calls ÷ steps), `frameMs` (whole frame) and `stepsPerFrame`, fed to `governorStep` once per second. Samples are discarded while the controller fast-forwards an opening (§4.3), while an e2e `advance` steps, and in Record mode (deterministic by construction, never degrades). The ladder reacts to the **render share** `frameMs − stepsPerFrame × stepMs`, never to the step cost: a sim-bound frame (the loop's 40 ms stepping budget plus render) must not drive the visual ladder, because no visual level can help it — the HUD line says `SIMULATION-BOUND` instead.
- **Ladder** (hysteresis: raise one level after 1.5 s of render share above target, lower one level after 6 s below 70 % of target; never two levels per second): level 0 nothing; **1** effect spawn density × 0.5 (sparks, slag, drips, far-spark spawn rate); **2** `REDUCED_FACTOR`/`POINT_FACTOR` × 0.6 and `FIGHTER_POINT_DISTANCE` × 0.6; **3** engine-glow sprites and ionised trails hidden, barrier shells ≤ 6 visible; **4** far sparks ≤ 2,048, death debris ≤ 128, one near beam pair (rest in `farBeams`). The simulation is never touched by any level: the same seed gives the same result at level 0 and level 4 (asserted).
- **Budget**: `budgetFromLadder` turns the measured ladder (§21.5) into `PerfBudget`; the controller also refines it in play through `refineBudget`, which lowers `liveHullsPerSide` to `min(budget, round(0.8 × live))` **only** when level 4 has been held for `refineAfter` (20 s) **and** the render share is still over target (a sim-bound frame never refines), never below `budgetFloor` (100), never in Record mode or during a fast-forward, and never in the Playwright profile (`navigator.webdriver`), so e2e runs persist nothing. Persistence: `prefs.perf = { budget: PerfBudget; governor: boolean }` (`core/storage.ts`, CORE); `governor: false` disables the ladder (a settings toggle) but never the warnings. **The budget only warns** (editor, briefing, HUD line): no engagement size, no battle outcome and no campaign depends on it (§21.4). Headless and tests use `DEFAULT_PERF_BUDGET`.
- **Warnings, never caps**: the custom editor (B1/B2, §6) and the briefing (`This order of battle fields 640 live hulls per side against a measured budget of 420. Expect reduced effect density and LOD distance; the simulation stays exact.`) warn when `totals.hulls > budget.liveHullsPerSide`; both have a `Scale to budget` button and both launch regardless. HUD clock line (stage B): `LIVE HULLS 640 · BUDGET 420 · GOVERNOR 2`. A "Re-measure performance budget" button in Settings runs the in-browser ladder (§21.5) and stores the result.

### 21.3 Flights (`src/simulation/flights.ts`, CORE)

When a side's live small craft (fighters and Oculi, counting flight members) would exceed `FLIGHT_THRESHOLD = 64` per side, every further launch creates a **flight** instead of single craft: one `ShipState` with `flight: { craft: 4; maxCraft: 4; classId }`, hull pool `4 × craft hull`, armour and barriers per craft, point value `4 ×`, speed/turn of the craft; damage removes one member per `craft hull` lost (`flight_member_lost` event), weapons fire `craft` shots per volley (one `weapon_fired` event with `shots: 4`), target scoring treats it as four craft; `lossesByClass` and `fighters_launched` count craft, not flights; `escaped` on carrier recovery returns the surviving members to the hangar. The decision is deterministic (depends only on live counts at launch time). Rendering (stage A): four instanced small craft in a finger-four pattern (offsets `(0,0,0)`, `(−0.4,0,−0.5)`, `(0.4,0,−0.5)`, `(−0.8,0.1,−1.0)` × lengthUnits) about the flight position; far: one point per member.

### 21.4 Campaign engagement scaler and the remainder

`CampaignState.engagementScale: number` is **fixed at campaign creation** (default `DEFAULT_PERF_BUDGET.liveHullsPerSide` = 400; the setup screen offers `Engagement size: 200 / 400 / 800 live hulls per side`, stage C; `normaliseCampaign` fills 400 for older snapshots and the CHANGELOG says old campaigns now field up to 400 hulls per side instead of 70). `buildEngagement(state, pending)` uses it and nothing else: `kA = min(1, state.engagementScale / alliedTotal)`, `kB` likewise; hulls compressed away are emitted as `config.distant.groups` per fleet (`count = total − simulated`, class mix from the fleet's counts, canon captions = percentages only), so a 1,500-hull campaign fleet is still represented and its losses are scaled back as today (the layer's statistical losses are **not** applied to the campaign; only the real battle's result is, unchanged from v0.11). `autoResolve` (a headless `BattleSimulation` of the same config) and the 3D path therefore build the same battle, and two players with the same seed get the same war on any machine. The measured `prefs.perf.budget` is used only for the briefing warning when `engagementScale > budget.liveHullsPerSide`.

### 21.5 Benchmark ladder (`npm run perf`, published in `docs/apex/PERF_LADDER.md`)

- `scripts/perf-sim.ts` (headless, node): for each of 100 / 300 / 600 / 1,000 hulls per side, build a mixed canon custom battle (per side: dreadnoughts 6 %, carriers 2 %, cruisers 32 %, frigates 60 % for the coalition; capitals 25 % / destroyers 75 % for the Reaper side; seed 11; deep space 80 km), run 1,200 steps after a 200-step warm-up, report **steps/s**, **steps per 16.7 ms frame**, projectiles in flight, grid cells, and the time split (movement / weapons / projectiles / AI) from `sim.profile`. Also the brief's named row **300 vs 100**.
- `scripts/perf.mjs` (Playwright, SwiftShader, as today): the same ladder in the browser: `drawCalls`, ms/frame at tactical and follow cameras, governor level reached, LOD counts; it writes `docs/apex/PERF_LADDER.md` with a machine string.
- **Baseline (reviewer measurement, 1 November 2026, v0.11 `buildCustomBattle` v1 shape, canon, seed 11, this container)**, recorded here so the gate is measured against something and not assumed (`CINEMATIC_DESIGN.md` §7.2 said "to be measured"): 100 vs 100 = 4.35 ms/step (230 steps/s); 300 vs 100 = 12.35 ms/step before contact and 18.1 ms/step in the firing phase (81 and 55 steps/s, i.e. 1.4 and 0.9 steps per 16.7 ms frame); 300 vs 300 = 37 ms/step; the old "400 steps < 4 s" bound already fails at 4.9–7.2 s. CPU profile of the firing phase: `tryFire` 64.8 % self time (every `antiSmall` mount scans `enemiesOf()` on every tick while idle because a mount with no target returns without setting a cooldown; main guns re-scan every enemy for a target of opportunity), GC 13.5 % (`vec3` allocation in `weaponWorldOffset`/`tryFire`), `movementGoal` 7.2 %. The gate therefore needs a 15–22× speed-up **before** Oculi, flights, solutions, M1/M2 and movement add cost, and T8 (`WORK_BREAKDOWN.md`) re-measures this baseline on the dev machine into `CALIBRATION_REPORT.md` §0 before touching anything. **HEADLESS_GATE** = `{ stepsPerFrame: 20 }` (`scripts/perf-sim.ts`).
- **Algorithmic levers (T8, mandatory, in this order)**: an idle-mount retry cooldown (`IDLE_RETRY_S = 0.25`, **TUNE** 0.25–0.5, deterministic) set whenever `tryFire` finds no target; one grid query per ship per tick for "any enemy within this ship's longest weapon range" that skips `updateWeapons` entirely when false; allocation-free distance checks in `tryFire`/`weaponWorldOffset` (squared distances on scalars, scratch vectors); weapon world offsets cached per ship per tick; then the grid for projectiles, PD and targeting (T8 as before). Only then the tuning levers: grid cell size (4 → 6 km), decision stagger (0.25 → 0.4 s), projectile `ttl` cap for misses beyond 2.2 × range, beam-tick damage batching (apply every 2 ticks with the same total), and last the flight threshold (64 → 48). Never the fixed step.
- **Gate (brief §8.2 check)**: the 300-vs-100 headless row at ≥ 20 steps per wall-clock frame (≥ 1,200 steps/s) on the dev machine is the **target**. `tests/perf.test.ts` asserts a **scaling** bound, not an absolute one: the per-step cost of 300 vs 100 is ≤ 4 × that of 100 vs 100 measured in the same process (both after a 200-step warm-up, 400 steps), plus a generous absolute ceiling (400 steps of 300 vs 100 < 20 s) as a smoke test, plus `SpatialGrid.querySegment`/`queryRadius` ≡ brute force; the e2e Battle of Earth still completes; `tests/governor.test.ts` covers the ladder. If the target is missed after every lever above, `PERF_LADDER.md` and the CHANGELOG print the measured 300-vs-100 figure, name the **largest ladder row that meets 20 steps per frame**, and INTEGRATION asks the owner to approve that fallback in writing (rule 5); nothing is "recorded" silently and no document claims the gate holds unless it does.
